# usque в Docker

[English version →](README.en.md)

Контейнер с [usque](https://github.com/Diniboy1123/usque) — неофициальным клиентом
Cloudflare WARP по протоколу MASQUE (HTTP/3 поверх QUIC, есть и режим HTTP/2).

Даёт машине выход в интернет через WARP: как полноценный TUN-интерфейс (весь IP-трафик),
как SOCKS5/HTTP-прокси или как проброс портов в сеть WARP. Поддерживаются WARP-аккаунт и
Cloudflare Zero Trust, маршрутизация настраивается, а если провайдер фильтрует соединение
по SNI — есть обход.

## Возможности

* **Все режимы usque**: `tun`, `socks`, `http-proxy`, `l4-socks`, `l4-http-proxy`, `portfw`.
  Переключаются переменной `USQUE_MODE`; несколько можно запустить одновременно в одном контейнере.
* **TUN с любым именем интерфейса** (`USQUE_IFACE`), настройка MTU, режим «не трогать адреса».
* **Маршрутизация внутри контейнера**: `ROUTE_MODE=none|main|table` — от «не вмешиваться»
  до отдельной таблицы маршрутизации с правилом `ip rule`. Обход MASQUE-эндпоинта
  (без него получилась бы петля) делается автоматически.
* **Zero Trust**: регистрация по team-токену, автоматическая подстановка нужного SNI,
  обновление ключа при старте.
* **Обход DPI**: подмена SNI (`USQUE_SNI`) и работа через TCP, если провайдер режет QUIC.
* **Мультиарх**: `linux/amd64`, `linux/arm64`, `linux/arm/v7`.
* **Готовый CI**: тесты, мультиарх-сборка и публикация образа — [.gitlab-ci.yml](.gitlab-ci.yml).

## Требования

| | Для `tun` | Для прокси-режимов |
|---|---|---|
| Драйвер `tun` в ядре хоста | **обязателен** | не нужен |
| Docker с поддержкой `cap_add` и `device_cgroup_rules` | нужен | нужен |
| Дополнительные capability | `NET_ADMIN` | не нужны |
| Доступ в интернет к Cloudflare | нужен | нужен |

Проверить, умеет ли ваше ядро TUN:

```bash
grep -i tun /proc/misc      # драйвер зарегистрирован в ядре?
modprobe tun                # если он собран модулем
```

Пусто и модуля нет (`# CONFIG_TUN is not set` в конфиге ядра) — TUN-режим на таком хосте
не заработает, понадобится другое ядро. Пользовательские режимы — `socks`, `l4-socks`,
`http-proxy` — работают в любом случае: они целиком в userspace.

## Быстрый старт

```bash
git clone https://github.com/incognito1990/usque-docker.git && cd usque-docker
cp .env.example .env
docker compose up -d --build
docker compose logs -f usque
```

При первом запуске контейнер сам зарегистрирует новое устройство WARP и сохранит конфиг
в `./config/config.json` — там приватный ключ устройства, файл не стоит никому показывать
(в git он не попадает, `.gitignore` его исключает). Если конфиг уже существует и заполнен,
регистрации не будет.

Убедиться, что трафик идёт через WARP:

```bash
docker compose exec usque curl -s https://1.1.1.1/cdn-cgi/trace | grep -E '^(ip|warp)='
```

Ожидаемый результат — `warp=on` и адрес выхода Cloudflare, а не адрес вашего провайдера.
Для socks-режима то же самое снаружи:

```bash
curl -x socks5h://127.0.0.1:1080 https://1.1.1.1/cdn-cgi/trace | grep warp
```

## Режимы работы

| `USQUE_MODE`   | Что даёт | Порт |
|----------------|----------|------|
| `tun`          | TUN-интерфейс, весь IP-трафик (по умолчанию) | — |
| `socks`        | SOCKS5, включая UDP ASSOCIATE | `USQUE_SOCKS_PORT` (1080) |
| `http-proxy`   | HTTP-прокси с CONNECT | `USQUE_HTTP_PORT` (8000) |
| `l4-socks`     | SOCKS5 только для TCP, быстрее обычного (QUIC-стримы) | 1080 |
| `l4-http-proxy`| HTTP-прокси только для TCP | 8000 |
| `portfw`       | Проброс портов в сеть WARP и обратно | — |
| `register`     | Зарегистрировать устройство и выйти | — |
| `enroll`       | Переобучить ключ и выйти | — |

Несколько режимов сразу — задайте порт дополнительного:

```bash
USQUE_MODE=tun
EXTRA_SOCKS_PORT=1080     # плюс SOCKS5
EXTRA_HTTP_PORT=8000      # плюс HTTP-прокси
```

Каждый режим поднимает свой туннель в том же контейнере. Если любой из процессов
завершится, контейнер остановится — это видно в `docker compose ps` и в логах.

Разовая команда без запуска контейнера:

```bash
docker compose run --rm -e USQUE_MODE=register usque   # новое устройство
docker compose run --rm -e USQUE_MODE=enroll usque     # обновить ключ
make dryrun                                            # показать команду, ничего не запуская
```

## Настройка

Все переменные с пояснениями — в [.env.example](.env.example). Основные:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `USQUE_MODE` | `tun` | режим работы |
| `USQUE_CONFIG` | `/etc/usque/config.json` | путь к конфигу внутри контейнера |
| `USQUE_REGISTER` | `auto` | `auto` — зарегистрировать, если конфига нет; `force` — создать новое устройство взамен; `never` — не трогать |
| `USQUE_IFACE` | `usque-tun` | имя TUN-интерфейса, до 15 символов |
| `USQUE_SNI` | как в usque | подставить свой SNI (Zero Trust, обход DPI) |
| `USQUE_JWT` | — | team-токен Cloudflare Zero Trust |
| `ROUTE_MODE` | `main` | `none` / `main` / `table` — см. «Маршрутизация» |
| `ROUTE_TABLE` | `100` | номер таблицы для `ROUTE_MODE=table` |
| `ROUTE_EXCLUDE` | — | подсети, которые всегда идут мимо туннеля |
| `ROUTE_IPV6` | `auto` | трогать ли IPv6-маршрут по умолчанию |
| `USQUE_BIND` | `0.0.0.0` | адрес, на котором слушают прокси |
| `USQUE_PROXY_USER`, `USQUE_PROXY_PASS` | — | логин и пароль прокси |
| `USQUE_HTTP2` | `0` | `1` — работать по TCP+TLS вместо QUIC |
| `USQUE_MTU` | `1280` | MTU туннеля |
| `USQUE_EXTRA_ARGS` | — | произвольные аргументы в конец команды usque |

Правки применяются перезапуском: `docker compose up -d` (при изменении `.env`) или
`docker compose restart usque`.

Порты публикуются только на `127.0.0.1` — прокси без авторизации, доступный всей сети,
превращается в открытый прокси. Нужен доступ с других машин: поменяйте проброс портов
в `docker-compose.yml` и обязательно задайте `USQUE_PROXY_USER`/`USQUE_PROXY_PASS`.

## Zero Trust

Получите team-токен: Zero Trust Dashboard → Settings → WARP Client → Device enrollment.
Дальше достаточно двух строк в `.env`:

```bash
USQUE_JWT=<team-токен>
USQUE_REGISTER=auto
```

Контейнер зарегистрирует устройство в вашей организации и **сам подставит нужный SNI**
(`zt-masque.cloudflareclient.com`) — дефолтный SNI обычного WARP для Zero Trust не подходит.
Признак сохраняется в `config/.zerotrust`, поэтому следующие запуски тоже используют верный SNI.

Токены Zero Trust живут недолго, поэтому разумно включить обновление ключа при старте:

```bash
USQUE_ENROLL_ON_START=1
```

Если у вас есть готовый конфиг с другого устройства, положите его в `./config/config.json`.
Для Zero Trust в нём меняются только `id` и `access_token`; шаблон со всеми полями —
[config/config.zerotrust.example.json](config/config.zerotrust.example.json).

Ограничения режимов `l4-*`: у них нет возможности задать SNI (он зашит как
`consumer-masque-proxy.cloudflareclient.com`) и они работают только поверх QUIC.
Контейнер сам отфильтрует неподдерживаемые флаги и предупредит в логе.

## Маршрутизация

usque не добавляет маршруты — он только поднимает интерфейс и назначает адреса. Всё
остальное делает [hooks/route-hook.sh](hooks/route-hook.sh), который usque вызывает после
каждого подключения и разрыва.

```bash
ROUTE_MODE=none      # не трогать маршруты вообще
ROUTE_MODE=main      # маршрут по умолчанию через TUN в основной таблице   ← по умолчанию
ROUTE_MODE=table     # то же, но в отдельной таблице + правило ip rule
```

| | `main` | `table` |
|---|---|---|
| Маршрут по умолчанию | в основной таблице | в таблице `ROUTE_TABLE` + `ip rule lookup <таблица> priority 1000` |
| Обход MASQUE-эндпоинта | `/32` через шлюз контейнера | и в основной таблице, и в таблице |
| Локальные сети | доступны как обычно | копируются в таблицу маршрутизации |
| При разрыве туннеля | прежний маршрут возвращается | маршрут убирается из таблицы, правило остаётся и трафик уходит в основную таблицу |
| Основная таблица | изменяется | не изменяется |

Выбирайте `main`, если контейнер — единственный шлюз и вы хотите привычную картину;
`table`, если не хотите менять основную таблицу (например, в той же сетевой области
работают другие VPN). `none` — если маршрутами занимается что-то другое.

Почему отдельная таблица требует копирования маршрутов: она не дополняет основную, а
полностью подменяет её для выбранного трафика, поэтому её `default` перехватывает в том
числе шлюз Docker. Без копирования отвалились бы ответы клиентам docker-сети, например
опубликованному порту прокси.

Обход эндпоинта обязателен всегда: сначала добавляется маршрут `/32` до MASQUE-эндпоинта
через шлюз, и только потом меняется маршрут по умолчанию. Иначе пакеты до эндпоинта уходили
бы в туннель, возвращались в usque — и получалась петля. Шлюз запоминается при старте
контейнера, до запуска usque.

Исключения из туннеля — списком подсетей:

```bash
ROUTE_EXCLUDE="10.0.0.0/8 192.168.0.0/16"
```

## Обход блокировок: SNI и DPI

Если прокси слушает порт, но первый же запрос через него висит, а в логе есть
`Establishing MASQUE connection...` и тишина — соединение режет DPI провайдера по имени
домена (SNI). Помогает подстановка SNI домена, который через этот фильтр проходит:

```bash
USQUE_SNI=example.com
```

`example.com` здесь — заглушка. Нужен реальный домен, который доступен у вашего провайдера
и обслуживается Cloudflare. Сертификат эндпоинта при этом по-прежнему проверяется — по ключу
из вашего конфига, а не по имени, поэтому подмена SNI не ослабляет защиту.

Если не помогло — попробуйте `USQUE_HTTP2=1`: соединение пойдёт по TCP+TLS вместо QUIC/UDP.
Это помогает и там, где провайдер просто блокирует UDP. Учтите, что режимы `l4-*` работают
только поверх QUIC и этот флаг не поддерживают.

## DNS

По умолчанию контейнер использует резолвер Docker (`127.0.0.11`), который резолвит на
стороне демона, то есть **мимо туннеля**. Чтобы DNS-запросы шли через WARP, в
`docker-compose.yml` нужно указать `dns:` со своим резолвером.

Но включайте это осознанно: в сетях с фильтрацией DNS прямой запрос к публичным резолверам
может не проходить вообще. Тогда контейнер останется без резолва — будут падать и
регистрация, и работа API. Если такое произошло, верните встроенный резолвер Docker
(закомментируйте `dns:`).

Клиенты, которые делят сетевую область с контейнером (`network_mode: service:usque`),
свой DNS прописывают самостоятельно — иначе они останутся на резолвере Docker.

## Сборка из исходников

```bash
make build          # образ для текущей архитектуры
make buildx         # мультиарх; с REGISTRY=... — сразу пуш в реестр
```

Сам usque собирается из апстрима; его версия задаётся переменной `USQUE_REF` — ветка, тег
или конкретный коммит, в `.env` или как `--build-arg`.

Образ для чужой архитектуры требует эмуляции на этапе установки пакетов (`make binfmt`,
нужен `--privileged`), потому что финальная стадия — alpine с `apk add`. Появление ошибки
`exec /bin/sh: exec format error` означает ровно это. Собирать на машине нужной архитектуры
или в CI проще — эмуляция не нужна.

## Диагностика

```bash
make help          # список команд
make dryrun        # показать итоговую команду usque и выйти
make shell         # bash внутри контейнера
make logs          # логи
docker compose ps  # состояние и healthcheck
```

| Симптом в логе | Причина и что делать |
|---|---|
| `Failed to create TUN device: no such device` | в ядре хоста нет драйвера `tun` — см. «Требования» |
| `Failed to create TUN device: operation not permitted` | контейнеру не дали `NET_ADMIN` |
| `Failed to get private key` / конфиг неполный | конфиг не создан: `USQUE_REGISTER=auto` или `docker compose run --rm -e USQUE_MODE=register usque` |
| Туннель поднялся, интернета нет | `ROUTE_MODE=none`, либо хук не отработал: `docker compose logs usque \| grep route` |
| Запрос висит, в логе только `Establishing MASQUE connection` | DPI не пропускает SNI — см. «Обход блокировок» |
| `warp=off` при проверке через прокси | трафик идёт мимо туннеля: проверьте `ROUTE_MODE` и `dns` |
| Долгий резолв или он не работает вовсе | конфликт с `dns:` — см. «DNS» |
| `failed to sufficiently increase receive buffer size` | не критично; на хосте можно поднять `sysctl -w net.core.rmem_max=7500000 net.core.wmem_max=7500000` |

## Тесты

```bash
make test-routes   # маршрутизация: main/table/none, обход эндпоинта, повторное подключение
make test-modes    # сборка аргументов всех режимов
```

Оба запускаются в одноразовых контейнерах: маршрутизация проверяется в изолированной
сетевой области, командная строка — на фиктивном конфиге, наружу ничего не уходит и ничего
не регистрируется. Проверки TUN-режима пропускаются автоматически, если в ядре нет драйвера.
